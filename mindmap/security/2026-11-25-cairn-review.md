# Security review: the CAIRN line (V0.9.68)

> **Date:** 2026-11-25 · **Code:** V0.9.67 reviewed, fixes in V0.9.68 · **Line:** [0.9 CAIRN harness plan](../plans/2026-11-22-0.9-cairn-harness.md) · **Release row:** [V0.9.68](../RELEASES_0.9.md)

## Scope and method

The surfaces added in V0.9.40 to V0.9.67: the tool loop and its evidence handles, the injection rules and corpus (V0.9.42), proposals and changesets, personal memory (V0.9.51), chat search (V0.9.52), corrections and decision offers (V0.9.53), playbooks (V0.9.54, V0.9.55), memory upkeep (V0.9.56), shared chats (V0.9.57), task tools and proposals (V0.9.58, V0.9.59), chats across workspaces and the provider boundary (V0.9.60, V0.9.61), large analyses (V0.9.62), routines and event routines (V0.9.63, V0.9.64), the review tool (V0.9.65), the MCP endpoint and the inbox (V0.9.66, V0.9.67). For each, the code was read looking for: content from outside the workspace that can reach a model and then a write or a persistent store; data of one person, workspace or role that reaches another; a limit or a policy that can be skipped; work that continues as someone who lost the right to do it; and what is kept and for how long. **This is a review by reading the code and reasoning about it. Nothing was run, no scanner was used, no penetration test was done and the injection corpus was not run against a model.** The regression tests named below compile and were not executed.

## Findings

| # | Severity | Finding | Status |
|---|---|---|---|
| CR-1 | **Medium** | A chat across all of a person's workspaces (V0.9.60) stores in its home workspace the files and cards other workspaces returned. V0.9.57 let its owner **share** it with the home workspace, so people who cannot read the other workspaces could read what came from them. The same held for the *CAIRN inbox* chat | **Fixed:** `share_agent_conversation` refuses a chat across workspaces and an inbox chat. Test `a_chat_across_workspaces_and_the_inbox_cannot_be_shared`. A chat across workspaces that was already shared before this fix stays shared until its owner stops sharing it |
| CR-2 | **Medium** | A routine (V0.9.63) checked that its owner still had a role that can write, but not that the **account was still active** nor that the workspace's **AI policy** still let that role use AI. A deactivated owner's routines kept running as them; an owner whose role fell below the AI minimum kept getting AI-written posts (the run itself answered without the model, but recorded a success and kept running weekly) | **Fixed:** `reason_not_to_run` pauses the routine, with the reason and a notification, when the account is deactivated or the AI policy excludes the owner's role |
| CR-3 | **Medium** | `record_correction` (V0.9.53) writes text into the person's **later system prompts**, with no confirmation. A document, issue or mail read in the same request could instruct the model to call it, which would persist an attacker's sentence in every later run of that person (bounded to 400 characters, 5 shown, marked *not yet reviewed, not evidence*) | **Fixed:** the tool refuses in a request that read content from outside the workspace (`gathered.untrusted` is not empty), telling the model to ask the person to say it again. **Residual:** a file inside the workspace written by a colleague is not "outside" and can still steer the model to record a correction; the correction is shown to the model as unreviewed and never as evidence |
| CR-4 | Medium, **open** | Memory upkeep (V0.9.56), when an administrator turns it on, lists in the review queue the **text of a question** that at least two people asked three times and got no answer to. Chats are private ("only you can see them"), so those words reach every writer of the workspace | **Open.** Proposed fix: show only a count and the words the questions share, or let each person opt in; until then the setting's description and the changelog say it lists the question |
| CR-5 | Low, **open** | Shared chats (V0.9.57) show a reply as it was stored. A reply written in a run that used **personal memory** (V0.9.51) may restate a preference of its owner; the owner chooses to share, but is not told this | **Open.** Proposed fix: say so in the share confirmation, and mark replies made with personal memory |
| CR-6 | Low, **accepted** | An outside agent can fill the owner's inbox to its 50 pending proposals (V0.9.67), so that proposals of another token of theirs are refused until they dismiss some | The bound is the protection; the agent is told the inbox is full. Nothing is applied |
| CR-7 | Low, **open** | Event routines (V0.9.64) are noticed by the maintenance pass, and a flood of indexed files runs at most one routine per 15 minutes but each run reads as its owner with the full read tools and the owner's AI allowance | **Open.** Proposed fix: a daily cap of runs per routine |
| CR-8 | Info | Reviewed with no finding, **by reading**: the loop gives tools only the workspace's ledger and the person's own role, and a viewer is given no proposing tool (V0.9.10, V0.9.58, V0.9.59); every proposal, including those from MCP, waits for the owner and runs through the handlers the person would call, with the version of the task they read; personal memory is the owner's alone in storage and in prompts and is removed with the account; chat search returns only the caller's own chats and chats shared with the workspace and never a deleted one; the provider boundary builds the request only from passages the workspace, the role, the provider and the allowance permit, and a held-back passage is not in the request (test on the mock provider's body); a routine runs read-only and proposes nothing; an MCP token reaches only `/v1/mcp`, only its workspaces, with no write, with the same rate limit, and each call is recorded; an inbox proposal is quoted as data and names its client as an untrusted source; playbooks never grant a tool and only verified ones are offered; trace retention is `REPOMEMO_CAIRN_TRACE_DAYS` | none |
| CR-9 | Info | **Not reviewed:** the injection corpus of V0.9.42 was not extended or run for this review (there is no model to run it against here); the MCP handshake and client configurations were not tried with a real client; the server-side decision across workspaces (role, policy, provider, allowance of each) has no test that drives it | The live evaluation of V0.9.70 is where these are tried |

No high finding. **Open: CR-4, CR-5 and CR-7**, and the residual of CR-3.
