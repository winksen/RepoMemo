# Plan for the rest of the 0.9 line: CAIRN as a harness over governed evidence

Written 2026-11-22 for V0.9.33. Baseline: V0.9.32. Scope is rows V0.9.33 to V0.9.69 and V0.9.119 in the [release index](../RELEASES_0.9.md) and the [roadmap](../ROADMAP.md#the-09x-line-cairn-agent). Why: the [CAIRN agent review](../analysis/2026-11-22-cairn-agent-review.md). Decision: [ADR 0006](../../docs/decisions/0006-cairn-is-a-bounded-tool-loop-over-governed-evidence.md). The pilot rows that used to follow V0.9.32 are now the [0.10 line](../RELEASES_0.10.md), unchanged.

This plan is written for the session that implements it. Each row below is one commit named `Update V0.9.N`, with the usual body (three or four `- ` lines), the version set with `npm run version:set -- 0.9.N`, the changelog, the user guide when something visible changes, and the roadmap, release index and mindmap rows updated together. Follow [CLAUDE.md](../../CLAUDE.md): no server, build, Vite or Tauri run; `cargo fmt --all`, `cargo clippy -D warnings`, `cargo check` and `npm run typecheck` when the maintainer allows them; a row is 🧪 until the maintainer has tried it.

## The contracts this line rests on

### 1. Provider contract (V0.9.34, V0.9.35, V0.9.36)

```rust
// crates/ai/src/lib.rs
pub enum ChatRole { System, User, Assistant, Tool }
pub struct ChatMessage { pub role: ChatRole, pub content: String, pub tool_calls: Vec<ToolCall>, pub tool_call_id: Option<String> }
pub struct ToolSpec { pub name: String, pub description: String, pub parameters: Value /* JSON Schema object */ }
pub struct ToolCall { pub id: String, pub name: String, pub arguments: Value }
pub struct ChatRequest { pub messages: Vec<ChatMessage>, pub tools: Vec<ToolSpec>, pub options: Value }
pub struct ChatResponse { pub content: String, pub tool_calls: Vec<ToolCall>, pub finish: FinishReason, pub usage: Option<Usage> }
pub struct Usage { pub input_tokens: u32, pub output_tokens: u32 }
pub enum ToolMode { Native, Json, None }
pub struct ModelTraits { pub tool_mode: ToolMode, pub context_tokens: u32 }
```

- `generate` stays and is implemented once on top of `chat` (system + one user message), so no existing caller changes.
- OpenRouter and every OpenAI-compatible endpoint use `/chat/completions` with `tools`; Ollama uses `/api/chat` with `tools`.
- `ModelTraits` live in the provider's `metadata` JSON (`tool_mode`, `context_tokens`), filled by *Test connection* (a tiny tool call: answered with a tool call → `native`; valid JSON to the JSON protocol → `json`; else `none`) and editable by an administrator. No migration.
- **JSON protocol** for `ToolMode::Json`: the system prompt lists the tools and asks for exactly one object per reply, `{"tool": "<name>", "arguments": {...}}` or `{"answer": "<markdown>"}`. An invalid reply is sent back once with the parse error; a second invalid reply ends the run with a partial answer.

### 2. Tools and effect classes (V0.9.37, V0.9.38)

```rust
// crates/api/src/agent/tools.rs
pub enum ToolEffect { Read, Propose }          // External is not representable in this line on purpose
pub struct CairnTool {
    pub name: &'static str,                    // snake_case, stable, part of the eval set
    pub description: &'static str,             // what the model reads
    pub parameters: fn() -> Value,             // JSON Schema
    pub effect: ToolEffect,
    pub requires_ai: bool,
    pub group: &'static str,                   // Find, Understand, Change (V0.9.32)
    pub capability: Option<AgentCapability>,   // the + menu job it backs, if any
}
pub struct ToolOutput {
    pub for_model: String,                     // compact text with evidence handles, bounded (default 6,000 chars)
    pub evidence: Vec<EvidenceItem>,           // what the handles point to
    pub reply_parts: ReplyParts,               // files, matches, memory cards, file set: what the client renders
    pub proposals: Vec<AgentProposal>,         // only for Propose tools
}
```

- **Read** tools run immediately with the person's rights. **Propose** tools only build `AgentProposal`s; `agent_proposals.rs` stays the only place where anything is applied.
- A viewer's tool list never contains a Propose tool (the V0.9.10 rule moves from the reply to the tool list; the reply check stays as a second line).
- Tool names (the loop's atoms, V0.9.38): `search_evidence`, `read_file`, `list_files`, `file_facts`, `find_symbol`, `recall_memory`, `workspace_brief`; composite jobs keep their names (`summarize_file`, `analyze_files`, `summarize_chat`); propose tools: `propose_memory`, `propose_memory_change`, `propose_note`, `propose_file_move`, `propose_file_rename`, `propose_trash`, `propose_status`. Later rows add `search_chats`, `load_playbook`, `list_tasks`, `get_project`, `propose_task`, `propose_task_comment`, `propose_personal_memory`.

### 3. Evidence ledger (V0.9.38, V0.9.41, V0.9.42, V0.9.45)

- Every passage, file, card or task a tool returns gets a run-local handle: `E1`, `E2`… for passages and files, `M1`… for memory cards, `T1`… for tasks, `P1`… for playbooks. The model sees handles, never database ids.
- `EvidenceItem { handle, kind, artifact_id | card_id | task_id, chunk_id?, workspace_id, title, path, lifecycle_state, trust: Trusted | Untrusted(source), freshness?: Complete | Partial | Stale | Quarantined }`.
- The final answer cites handles as `[E3]`. The ledger check (V0.9.41) keeps handles that exist in this run, maps them to `Citation`s in the order cited (the V0.9.4 and V0.9.8 rules), removes the rest and adds a warning naming them.
- **Untrusted** (V0.9.42): connector items (issues, pull requests, Jira, imported chat), mail, files uploaded by guests, and anything in quarantine is never shown at all. Untrusted text goes to the model inside a fenced block that says it is quoted data. A proposal created after the run read untrusted evidence carries `provenance: { untrusted_sources: [...] }`, and the card says "Proposed after reading content from <source>".

### 4. Runs (V0.9.39, V0.9.40, V0.9.43)

- One person's message with the loop on starts a **run**. A run is bounded by `REPOMEMO_CAIRN_MAX_STEPS` (default 8 model calls), `REPOMEMO_CAIRN_MAX_RUN_SECONDS` (default 90), a token budget of half the model's `context_tokens` per call, and the workspace's AI quota (each model call consumes one unit, so a quota counts calls, not messages). Administrators can lower them per workspace in Settings › AI.
- A run ends as `answered`, `awaiting_confirmation` (it produced proposals), `partial` (a budget was reached: the answer says what was done and what was not), `failed` or `cancelled`.
- Tables (one migration, the next free number, `NNNN_agent_runs.sql`):

```sql
CREATE TABLE IF NOT EXISTS agent_runs (
  id TEXT PRIMARY KEY,
  turn_id TEXT REFERENCES assistant_turns(id) ON DELETE CASCADE,
  conversation_id TEXT NOT NULL REFERENCES assistant_conversations(id) ON DELETE CASCADE,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  origin TEXT NOT NULL CHECK (origin IN ('chat', 'routine', 'inbox')),
  provider_id TEXT, model TEXT, tool_mode TEXT,
  state TEXT NOT NULL CHECK (state IN ('running', 'answered', 'awaiting_confirmation', 'partial', 'failed', 'cancelled')),
  steps INTEGER NOT NULL DEFAULT 0, input_tokens INTEGER NOT NULL DEFAULT 0, output_tokens INTEGER NOT NULL DEFAULT 0,
  started_at TEXT NOT NULL, ended_at TEXT
);
CREATE TABLE IF NOT EXISTS agent_steps (
  run_id TEXT NOT NULL REFERENCES agent_runs(id) ON DELETE CASCADE,
  position INTEGER NOT NULL,
  kind TEXT NOT NULL CHECK (kind IN ('model', 'tool', 'proposal', 'answer', 'note')),
  tool TEXT, arguments_json TEXT, summary TEXT NOT NULL,     -- a one-line summary, never a full passage
  evidence_json TEXT NOT NULL DEFAULT '[]', duration_ms INTEGER NOT NULL DEFAULT 0, error TEXT,
  PRIMARY KEY (run_id, position)
);
```

- **Privacy:** a trace is personal like its conversation. It is deleted with the conversation, removed by account anonymization (`crates/storage/src/accounts.rs`), not part of workspace archives, and kept `REPOMEMO_CAIRN_TRACE_DAYS` (default 90) by the maintenance sweep. Steps store summaries and handles, not passage text. No per-person usage report is built from traces.

### 5. Memory layers (V0.9.48 to V0.9.56)

| Layer | Holds | Who writes | Who reads | Loaded how |
|---|---|---|---|---|
| Run scratchpad | Tool results of this run | CAIRN | This run | Messages of the run |
| Conversation summary | A rolling summary of turns that no longer fit, with the handles of their files | CAIRN, automatically | The chat's owner (and share readers) | Always, before the newest turns |
| Workspace instructions | `CAIRN.md` at the workspace root: how this team wants CAIRN to work | Writers, as an ordinary note; reviewed | Everyone in the workspace | Always, after the persona, capped (2,000 chars), never above the rules |
| Personal memory | Preferences and facts about one person (language, role, current focus) | CAIRN proposes, the person confirms; the person edits | That person only | Always, a frozen block of at most 1,200 chars at run start |
| Past chats | The person's own conversations | — | That person | `search_chats` tool, on demand |
| Team memory | Memory cards (revisions, citations, approvals) | CAIRN proposes, writers confirm, approvals as configured | Workspace readers | Relevant verified cards retrieved at run start (`M` handles); others on demand |
| Playbooks | Procedures in the `Playbooks` folder | CAIRN proposes, writers confirm; only `verified` ones are offered | Workspace readers | Names and one-line descriptions always; body via `load_playbook` |
| Upkeep findings | Contradictions, stale cards, unanswered questions | The upkeep job | Reviewers | Review queue, never the prompt |

Rule: **nothing CAIRN writes on its own can change what CAIRN tells someone else.** Only reviewed team memory, verified playbooks and `CAIRN.md` (a reviewed note) steer runs for other people.

### 6. Workspaces and providers (V0.9.60, V0.9.61)

- A chat has a scope: one workspace (as today) or **All my workspaces**.
- Search, file and memory tools over several workspaces reuse the fan-out of `POST /v1/search` and the person's read rights at call time; every item carries its workspace, and handles stay unique across them.
- A passage of workspace W is sent to provider P only if W has P's endpoint enabled as a text provider for the person's role (same `provider_type` and `base_url` host, AI min role allows the person, W's AI limit not exhausted). Otherwise the item is listed in the reply as *found in W, not sent to the AI*, with its link. This is checked per item, in code, not by the model.
- A proposal always names exactly one workspace and runs through that workspace's handlers.

### 7. Routines and background runs (V0.9.62 to V0.9.64)

- A routine is a saved prompt run as its owner on a schedule or an event, with **Read tools only**; its proposals wait in the owner's chat. A routine pauses when its owner loses write access to the workspace, when the provider is disabled, or after three failed runs.
- Background runs split a large set into batches handled by fresh sub-runs (map) and one run that writes the result (reduce). The limits are `REPOMEMO_CAIRN_BACKGROUND_MAX_FILES` (default 200) and the workspace's AI quota.

### 8. MCP surface (V0.9.66, V0.9.67)

- `POST /v1/mcp` speaks MCP over Streamable HTTP. It authenticates with a personal access token that has the new `mcp` scope, limited to the token's workspaces (V0.5 token workspaces).
- Tools exposed: `search_evidence`, `read_file`, `list_files`, `file_facts`, `recall_memory`, `find_symbol`, and `ask` only where the workspace's AI policy allows the token owner. The results carry RepoMemo links and the trust state of each source.
- `propose_memory` and `propose_note` from an outside agent create a pending proposal in the owner's **CAIRN inbox** chat. Nothing is applied until the owner confirms in RepoMemo.

## Excluded on purpose

| Not in this line | Why | Reopened when |
|---|---|---|
| CAIRN calling outside MCP servers, shell, web browsing | Combining private data, untrusted content and a way out lets injected text send data away | A per-tool allow list, egress review and a security review that tests injection end to end |
| Outbound messages (webhooks, chat destinations, mail) from CAIRN | Same reason; these already have their own approval flows | Same |
| Routines that apply changes | Writes always have a person confirming | A pilot shows the confirmation step is the bottleneck, and the change is reversible |
| Self-written skills that run without review | The OpenClaw skill campaign of Feb 2026 shows the risk | Never as a default |
| Agent-to-agent messaging between people's CAIRNs | Shared chats and the inbox cover the need | A pilot asks for it |
| Per-person productivity analytics from traces | Out of the product's promise (V0.9.34 of the old pilot plan, now V0.10.1) | Never |
| A native Anthropic or Gemini provider | OpenRouter and the OpenAI-compatible provider reach them | A provider feature (caching, documents) proves necessary |

- Each finding becomes a review-queue item with its evidence, assigned like any review. Nothing is edited.

### Track AS. Bounded autonomy

**V0.9.62 ✨ Background runs over large sets.**
- When a request covers more files than one run can read, the loop calls `analyze_files` in background mode: batches of eight files run as sub-runs with fresh context and return notes with handles; one reduce run writes the result. Progress (*24 of 60 files read*) and cancel use the live run events.
- Replaces the eight-file cap of V0.9.27 with `REPOMEMO_CAIRN_BACKGROUND_MAX_FILES`; the quota is checked before each batch, and an exhausted quota ends `partial` with the files not read listed.

**V0.9.63 ✨ Routines.**
- Migration `NNNN_agent_routines.sql`: `(id, workspace_id, owner_id, title, prompt, schedule, next_run_at, state active|paused, pause_reason, last_run_id)`. A writer creates a routine from a chat (*Run this every Monday*) or in CAIRN › Routines. Schedules reuse the recurring-task rules (`recurring.rs`).
- Runs use Read tools only (contract 7), post into a chat named after the routine, notify the owner, and can go in the owner's mail digest. At most 10 routines per workspace.

**V0.9.64 ✨ Event routines.**
- A routine may run on an event instead of a time: files indexed in a folder, a connector sync bringing new items, a file marked outdated, a review becoming overdue. Events are debounced (one run per routine per 15 minutes) and the run receives the event's items as handles.
- Example templates: *When new incident notes arrive, summarize them and propose a decision card*.

**V0.9.65 ✨ Review assistant.**
- For a file or card due for review, CAIRN drafts what changed since it was last verified (versions, newer files mentioning it, corrections) and proposes a state (`verified`, `needs review`, `outdated`) with its reasons. Offered from the review queue and as a routine template.
