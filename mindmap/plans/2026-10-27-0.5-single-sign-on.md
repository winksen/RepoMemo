# The 0.5.x line: single sign-on (the plan for the theme after 0.4.x)

> **Status:** **proposed on 2026-10-27** by `V0.4.67`, which closes the 0.4.x line. Single sign-on was the candidate recorded in V0.3.27 and set aside on 2026-10-25 for the deployment line; with the server and the client now deployable, it is proposed again as the theme of the next minor. Nothing here is built. The maintainer confirms the theme (decision 41) before `V0.5.0` is cut.
> **Detail:** the reasons, the reading of today's sign-in, the decisions and the risks are in [the single sign-on plan](2026-10-24-single-sign-on.md), written on 2026-10-24 and still true of the code except for its release numbers, which this page replaces.
> **Method:** the ten single-purpose releases of that plan, renumbered `V0.5.1`–`V0.5.10` after a `V0.5.0` that opens the line, built one by one and committed as `Update V0.5.N` with a short list, as 0.3.x and 0.4.x were. **Containers and the desktop app are part of the tests** from the start, because they are how the line is deployed now.
> **Related:** [roadmap](../ROADMAP.md) · [the 0.4 release index](../RELEASES_0.4.md) · [clean-install run](../technical/clean-install.md#6-the-04-run-containers-and-the-desktop-app-v0466) · [deployment security review](../security/2026-10-27-deployment-security-review.md)

## Why this next

The 0.4.x line made RepoMemo deployable by a team that is not its author: images on a registry with provenance, a quick start, a direct install with a service, a desktop app an administrator can hand out, guides and a troubleshooting page that CI keeps true. What still stops a larger organization from adopting it is sign-in: a person has an email and a password, and a leaver is removed by hand. Single sign-on moves who is a member, with which role, and when they leave, to the identity provider the organization already runs. Scale-out (PostgreSQL, object storage) is not what stops a team: the single-node server holds the targets of [performance.md](../technical/performance.md).

## What 0.4.x leaves, and what comes first

These are not features; they are what the maintainer has to do or decide for the 0.4 line to be finished, and the new line starts on them.

| Carried over | What closes it |
|---|---|
| The 0.4 clean-install run (nineteen steps and a record sheet) | The maintainer runs [§ 6 of the clean-install page](../technical/clean-install.md#6-the-04-run-containers-and-the-desktop-app-v0466) and fills the sheet; every row `ok` with no workaround is the entry condition of `V0.5.0` |
| The first tag, which has never run the release workflows | A tag publishes the images, the archives, the page and (with the keys) the signed update; the maintainer protects the `v*` tags first (review item X7) |
| Keys and certificates that do not exist yet | An update signing key and its public half as `REPOMEMO_UPDATE_PUBKEY`; a Windows code-signing certificate; an Apple Developer ID and notarization credentials; until then builds are unsigned and say so |
| Left out of 0.4 on purpose | Linux arm64 builds, and signed updates for Linux and macOS (the feed carries Windows only) |
| Tests written and compiled, not run | `cargo test -p repomemo-desktop` and `cargo test --workspace` on the maintainer's machine, as in the checklist of each 0.4 release |
| The web suite's 22 failing tests on Windows (`ResizeObserver` and the like) | Not a 0.4 defect; fixed in a release of their own or the test environment is given what it lacks |

## Decisions to confirm

| # | Decision | Proposal |
|---|---|---|
| 41 | **The theme of the 0.5.x line** | Single sign-on with OpenID Connect, first. SAML, SCIM provisioning and several providers at once stay later |
| 42 | **Passwords** | They stay for break-glass accounts and for servers that do not turn single sign-on on; turning them off is a server setting guarded by the rule that an administrator has signed in through the provider first (as in the earlier plan) |
| 43 | **The desktop app and the provider** | The sign-in goes through the system browser with a one-time code back to the app, never an embedded page, so the app's window keeps showing only the bundled client |
| 44 | **Numbering** | `V0.5.0` opens the line; `V0.5.1`–`V0.5.10` are built one by one; the next minor is cut after the maintainer's tests of a clean install with a provider |

The other decisions of the earlier plan (which claims are trusted, how an account is matched, what happens to existing accounts) stand as written there.

## How the line is tested

As in 0.4: no server is started in this work, so each release says what it did not run. The additions: a provider is simulated in the tests by a small local OpenID Connect issuer (its keys, its discovery document, its tokens), so the token checks have real cases (a wrong audience, a replayed nonce, an expired token, a key that is not the provider's); the compose job of CI gains a step that signs in through that issuer; and the clean-install page gets the provider steps with a real one.

## Risks and how the plan meets them

| Risk | Answer |
|---|---|
| Taking over an account through an unverified or reassigned address | Only `email_verified` addresses match; after the first sign-in the (issuer, subject) pair decides |
| Locking everyone out by turning passwords off | The refusal until an administrator has signed in through the provider; break-glass accounts |
| A provider's discovery call used to reach the internal network | The same address rules as the repository and tracker hosts: no private ranges unless allowed |
| The desktop app showing a provider's page in its window | The flow goes through the system browser; the window never leaves the bundled client |
| The line growing | One change per release; SAML, SCIM and several providers are left out on purpose |

## What the maintainer decides now

1. **The theme:** single sign-on (decision 41), or another (more connectors, assistant depth, scale-out; the roadmap's *Later* table lists them).
2. **The entry condition:** whether `V0.5.0` waits for the 0.4 record sheet, as proposed, or the two lines overlap.
3. **An identity provider to test with:** which one the maintainer can use for the clean-install run of `V0.5.10` (Keycloak, Entra ID, Google, Okta).
